# JiugeBKN 离线镜像打包说明

**适用对象**：在能上外网的机器上制作离线包的人。
**产出**：一个可以直接拷到内网机的 `jiuge-bkn-deploy` 目录（约 2.9 GB）。
**交付给现场后**：按同目录下的《内网部署说明.md》操作。

---

## 四、填写 `.env`

```powershell
cd E:\workspace\qy\openbkn\openbkn-deploy\docker
Copy-Item .env.example .env
```

打开 `.env`，按注释把所有 `CHANGE_ME_*` 换成强密码。生成随机密码：

```powershell
-join ((48..57)+(65..90)+(97..122) | Get-Random -Count 32 | ForEach-Object {[char]$_})
```

```bash
openssl rand -base64 24
```

注意：

- `OSS_CRYPTO_AES_KEY` 必须正好 32 个字符
- 密码不要包含空格和 `#`
- `JIUGEBKN_PUBLIC_BASE_URL` 可以先用 `http://localhost:8080`，**现场部署时由内网人员改成实际 IP**；启动时 OAuth 客户端的回调地址会按这个值自动更新
- 如果要同时服务多个客户，推荐每个客户单独一份 `.env`（重新生成密码），不要共用

`.env` 包含全部密码，交付时按敏感资料管理。

## 五、打包镜像

**先确认目标机架构**：在目标机执行 `uname -m`，`x86_64` 用 5.1，`aarch64` 用 5.2。两者产物不能互换。

### 5.1 x86_64（amd64）机器

Git Bash：

```powershell
cd E:\workspace\qy\openbkn\openbkn-deploy\docker
bash package-images.sh
```

纯 PowerShell：

```powershell
Set-Location E:\workspace\qy\openbkn\openbkn-deploy\docker
powershell -ExecutionPolicy Bypass -File .\package-images.ps1
```

只查看镜像清单、不导出：

```powershell
bash package-images.sh --list
```

脚本会先拉取 9 个运行期镜像（MariaDB、Redis、Kafka、OpenSearch、MinIO、Hydra、Nginx 等），再构建 14 个应用镜像。

> 因为 `compose.yml` 给运行期镜像设置了 `pull_policy: never`（保证内网机缺镜像时立即报错而不是联网拉取），打包机必须显式拉取一次。
>
> **注意**：`package-images.sh` 里的 `docker compose pull --ignore-buildable` 实际会被这条策略跳过（输出 `Skipped`），镜像已在本地时不影响结果；在全新机器上打包请改用下面的 `package-images-arm64.sh`，或手工 `docker pull` 补齐。

### 5.2 ARM（aarch64 / 鲲鹏 / 飞腾）机器

**x86 包不能给 ARM 机器用。**镜像里是编译好的机器码，ARM 内核无法执行 x86 指令；`docker load` 和 `docker compose up` 都不校验架构，包会正常导入、容器也能创建，但启动时 `exec format error`，配合 `restart: unless-stopped` 表现为**所有容器 `Restarting (255)`**。

ARM 机器必须用专用脚本出包：

```bash
cd openbkn-deploy/docker
bash package-images-arm64.sh
```

脚本固定以 `linux/arm64` 为目标平台，依次完成：

1. **拉取第三方镜像**：`docker pull --platform linux/arm64`。`oryd/hydra` 在国内代理被拒（403 不在白名单），自动改走 `ghcr.io/openbkn-ai/oryd/hydra` 再打回原名，见脚本顶部 `PULL_SOURCES`。
2. **准备构建期基础镜像**：`agent-observability` 的 Dockerfile 写死了 `gcr.io/distroless/static-debian12:nonroot`，国内直连会超时（`dial tcp 142.250.99.82:443`）。脚本自动从 `m.daocloud.io` 预拉 arm64 版本并**在本地打成原名**，BuildKit 直接从本地镜像存储取用。见 `BASE_IMAGE_SOURCES`。
   > 只 `docker pull` 而不 `docker tag` 回原名是无效的——BuildKit 仍会去 gcr.io 解析 tag。
3. **交叉构建 14 个应用镜像**：临时生成 `.compose-arm64.override.yml` 注入 `platform: linux/arm64`，再执行 `docker compose build`。
4. **校验架构**：逐个确认镜像为 `arm64`，任何一个不符就中止，不会产出混架构的包。
5. **导出**：`docker save --platform linux/arm64`。

分阶段执行（构建可能数小时，中断后可续跑）：

```bash
bash package-images-arm64.sh --list        # 看清单和当前架构
bash package-images-arm64.sh --pull-only   # 只拉第三方镜像（几分钟）
bash package-images-arm64.sh --build-only  # 只构建应用镜像（主要耗时）
bash package-images-arm64.sh --save-only   # 只校验并导出
```

> **耗时**：在 x86 机器上构建时全部 RUN 步骤走 QEMU 模拟，15 个镜像通常需要 3–10 小时。产物本身是原生 arm64，部署到 ARM 机器后没有性能损耗。
>
> 全流程日志写在 `build/package-arm64.log`，中断后可以从中查到卡在哪个服务。

### 5.3 产物

`openbkn-deploy\build\`：

| 文件 | 说明 |
|---|---|
| `jiuge-bkn-images.tar` | x86 包，23 个镜像（14 个应用 + 9 个运行期依赖），约 2.7 GB |
| `jiuge-bkn-images.tar.sha256` | 校验和 |
| `images.txt` | 镜像清单 |
| `jiuge-bkn-images-arm64.tar` | **ARM 包**，同样 23 个镜像，只含 `linux/arm64` |

## 六、核对与交付

### 6.1 校验产物

```bash
cd openbkn-deploy/build
sha256sum -c jiuge-bkn-images.tar.sha256
```

### 6.2 按架构拷贝

先确认内网机架构（`uname -m`：`x86_64` 或 `aarch64`），只拷对应目录即可。

```powershell
$src = "E:\workspace\qy\openbkn\openbkn-deploy"
$dst = "E:\to-intranet\jiuge-bkn-deploy"
New-Item -ItemType Directory -Force "$dst\docker","$dst\build" | Out-Null

Copy-Item "$src\docker\compose.yml","$src\docker\.env",
          "$src\docker\gateway.conf","$src\docker\proxy-headers.conf",
          "$src\docker\mariadb-init.sql","$src\docker\render-config.sh",
          "$src\docker\install-docker.sh","$src\docker\load-images.sh",
          "$src\docker\load-images.ps1",
          "$src\docker\镜像打包说明.md","$src\docker\内网部署说明.md" "$dst\docker"

Copy-Item -Recurse "$src\docker\config.template" "$dst\docker\config.template"

# 按架构二选一
Copy-Item -Recurse "$src\docker\app\amd64" "$dst\docker\app\amd64"
# Copy-Item -Recurse "$src\docker\app\arm64" "$dst\docker\app\arm64"

# 镜像包同样按架构二选一
Copy-Item "$src\build\jiuge-bkn-images.tar",
          "$src\build\jiuge-bkn-images.tar.sha256",
          "$src\build\images.txt" "$dst\build"
# Copy-Item "$src\build\jiuge-bkn-images-arm64.tar",
#           "$src\build\jiuge-bkn-images-arm64.tar.sha256",
#           "$src\build\images-arm64.txt" "$dst\build"
```

> 两个架构都要交付时，`app\` 下的两个子目录和两个镜像包可以一起拷，导入脚本会按本机架构校验并拒绝不匹配的包。

### 6.3 交付清单

- `docker\`（含 `.env` 与 `config.template\`）
- `docker\app\<架构>\`（Docker 安装包）
- `build\jiuge-bkn-images.tar` + `.sha256`

**不要**交付：`bkn-foundry`、`bkn-studio` 源码、`docker\config\`、另一架构的 `app\` 子目录、`build\` 下的历史产物。

## 七、常见问题

**构建时拉包失败**

构建阶段需要访问镜像仓库、Go 模块代理、PyPI、npm。仓库里已经配好国内镜像源；如果仍然失败，检查 Docker Desktop 的代理/DNS，或参考 `compose.yml` 顶部各服务的 `GOPROXY_URL`、`PIP_INDEX_URL`、`NPM_REGISTRY` 参数。

**磁盘空间不足**

构建缓存加镜像包通常需要 40 GB 以上；可执行 `docker system prune` 清理旧缓存后重试。

**镜像 tag 不对**

应用镜像统一命名为 `jiuge-bkn/<service>:<tag>`，`<tag>` 取自 `.env` 的 `JIUGEBKN_IMAGE_TAG`（默认 `local`）。改名后需要重新打包。

**内网机架构不一致**

amd64 的镜像包不能导入 arm64 机器。症状是**所有容器 `Restarting (255)`**，日志里是 `exec format error`——不是配置问题，是镜像包拿错了架构。

鲲鹏/飞腾机器用 `bash package-images-arm64.sh` 出包，详见 5.2 节。x86 机器上用 buildx + QEMU 交叉构建即可，不需要额外的 ARM 构建机。

导入端已经有硬校验：包架构和本机不一致时 `load-images.sh` / `load-images.ps1` 会在导入阶段直接失败，不会等到起容器才发现。
