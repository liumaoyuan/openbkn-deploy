# JiugeBKN 离线镜像打包说明

**适用对象**：在能上外网的机器上制作离线包的人。
**产出**：一个可以直接拷到内网机的 `jiuge-bkn-deploy` 目录（约 2.9 GB）。
**交付给现场后**：按同目录下的《内网部署说明.md》操作。

---

## 四、填写 `.env`

```powershell
cd E:\workspace\qy\openbkn\openbkn-deploy\docker
Copy-Item .env.example .env
```

打开 `.env`，按注释把所有 `CHANGE_ME_*` 换成强密码。生成随机密码：

```powershell
-join ((48..57)+(65..90)+(97..122) | Get-Random -Count 32 | ForEach-Object {[char]$_})
```

```bash
openssl rand -base64 24
```

注意：

- `OSS_CRYPTO_AES_KEY` 必须正好 32 个字符
- 密码不要包含空格和 `#`
- `JIUGEBKN_PUBLIC_BASE_URL` 可以先用 `http://localhost:8080`，**现场部署时由内网人员改成实际 IP**；启动时 OAuth 客户端的回调地址会按这个值自动更新
- 如果要同时服务多个客户，推荐每个客户单独一份 `.env`（重新生成密码），不要共用

`.env` 包含全部密码，交付时按敏感资料管理。

## 五、打包镜像

打包拆成两个脚本，各管一件事。**Windows（PowerShell）为主路径**，Git Bash / Linux 提供等价版本：

| 脚本 | 职责 | 产物 |
|---|---|---|
| `pull-images.ps1` / `pull-images.sh` | 只拉取镜像（第三方运行期 + 构建期基础），amd64 / arm64 并存 | 本地镜像 |
| `package-images.ps1` / `package-images.sh` | 只构建 + 导出，按架构出包 | `build/jiuge-bkn-images-<arch>.tar` |

**先确认目标机架构**：在目标机执行 `uname -m`，`x86_64` 对应 `--arch amd64`，`aarch64` 对应 `--arch arm64`。两者产物不能互换。

### 5.1 拉取镜像

**Windows（主路径）**：

```powershell
Set-Location E:\workspace\qy\openbkn\openbkn-deploy\docker

powershell -ExecutionPolicy Bypass -File .\pull-images.ps1                        # amd64 + arm64 全部（17 个镜像 × 2）
powershell -ExecutionPolicy Bypass -File .\pull-images.ps1 -Arch arm64            # 只拉 arm64
powershell -ExecutionPolicy Bypass -File .\pull-images.ps1 -Arch arm64 -Runtime   # 只拉 8 个运行期镜像
powershell -ExecutionPolicy Bypass -File .\pull-images.ps1 -Arch arm64 -Check     # 只核对本地架构，不拉取
powershell -ExecutionPolicy Bypass -File .\pull-images.ps1 -Clean                 # 删除清单内全部镜像（修复损坏记录）
```

**Git Bash / Linux**：

```bash
cd openbkn-deploy/docker

bash pull-images.sh                        # amd64 + arm64 全部（17 个镜像 × 2）
bash pull-images.sh --arch arm64           # 只拉 arm64
bash pull-images.sh --arch arm64 --runtime # 只拉 8 个运行期镜像
bash pull-images.sh --check --arch arm64   # 只核对本地架构，不拉取
bash pull-images.sh --clean                # 删除清单内全部镜像（修复损坏记录）
```

脚本按以下顺序尝试来源，成功即停：

1. **华为云 SWR**（`swr.cn-east-3.myhuaweicloud.com/openbkn-ai/...`）——仅限实测存在的镜像：`postgres:16`、`oryd/hydra`、`bitnami/kafka`、`model-factory-base`
2. 手工换源表：`oryd/hydra` → `ghcr.io/openbkn-ai/oryd/hydra`
3. `ghcr.io/xxx` → `ghcr.nju.edu.cn/xxx`；`gcr.io/xxx` → `m.daocloud.io/gcr.io/xxx`
4. 镜像原名直连（兜底；Docker Desktop 配了代理时会自动走代理）

> 华为云只收录**实测可用**的 4 个镜像，其余不上表——否则每个镜像都要先撞一次 404 再回退，反而更慢。换源后会自动 `docker tag` 回原名。

从镜像源拉下来后会自动 `docker tag` 回原名，`compose.yml` 不需要改。

> **为什么拉取不用区分架构标签**：Docker 的 containerd 镜像存储里，一个 tag 指向一个 manifest list，amd64 和 arm64 各存一份。`docker pull --platform amd64` 和 `--platform arm64` 拉两次即可并存。
>
> **为什么拉取不能顺带处理应用镜像**：`jiuge-bkn/*` 是构建出来的，拉取阶段还不存在。

### 5.2 构建并导出

**Windows（主路径）**：

```powershell
powershell -ExecutionPolicy Bypass -File .\package-images.ps1 -Arch amd64
powershell -ExecutionPolicy Bypass -File .\package-images.ps1 -Arch arm64
powershell -ExecutionPolicy Bypass -File .\package-images.ps1 -Arch both     # 依次打两个包
```

分阶段执行（构建可能数小时，中断后可续跑）：

```powershell
powershell -ExecutionPolicy Bypass -File .\package-images.ps1 -Arch arm64 -List        # 看清单和本地架构
powershell -ExecutionPolicy Bypass -File .\package-images.ps1 -Arch arm64 -BuildOnly   # 只构建
powershell -ExecutionPolicy Bypass -File .\package-images.ps1 -Arch arm64 -SaveOnly    # 只校验并导出
```

**Git Bash / Linux**：

```bash
bash package-images.sh --arch amd64
bash package-images.sh --arch arm64
bash package-images.sh --arch both        # 依次打两个包

bash package-images.sh --arch arm64 --list        # 看清单和本地架构
bash package-images.sh --arch arm64 --build-only  # 只构建
bash package-images.sh --arch arm64 --save-only   # 只校验并导出
```

每个架构依次完成：

1. **构建 15 个应用镜像**：临时生成 `.compose-arch.override.yml` 注入 `platform: linux/<arch>`，再执行 `docker compose build`
2. **校验架构**：逐个确认镜像为 `<arch>`，任何一个不符就中止
3. **导出**：`docker save --platform linux/<arch>`

### 镜像 tag 规则

**tag 直接等于架构名**：

```
jiuge-bkn/bkn-safe:amd64
jiuge-bkn/bkn-safe:arm64
```

两个 tag 天然并存，不会出现"后一次构建覆盖前一次"的问题，本地也不需要再额外打 `:local-amd64` 之类的标签。

> ⚠️ **目标机的 `.env` 必须与拿到的包一致**：
>
> ```
> JIUGEBKN_IMAGE_TAG=amd64    # 用 x86 包
> JIUGEBKN_IMAGE_TAG=arm64    # 用 ARM 包
> ```
>
> 填错时 compose 找不到镜像。`package-images` 会校验，`load-images.sh` 也会在检查不到镜像时提示这一点。

### 5.3 架构注意事项

**x86 包不能给 ARM 机器用。** 镜像里是编译好的机器码，ARM 内核无法执行 x86 指令；`docker load` 和 `docker compose up` 都不校验架构，包会正常导入、容器也能创建，但启动时 `exec format error`，配合 `restart: unless-stopped` 表现为**所有容器 `Restarting (255)`**。

**构建期基础镜像必须在本地**：`model-factory-base:v2`、`vega-python-base`、`gcr.io/distroless/...` 三个国内不稳定，由 `pull-images.sh` 自动换源。它们不进交付包，但构建时缺一个就编不出来。

**交叉构建耗时**：在 x86 上打 arm64 包时所有 `RUN` 走 QEMU 模拟，15 个镜像预计数小时；在 ARM 机器上原生构建则与普通构建相当。

**OpenSearch 使用自建镜像**：官方 `opensearchproject/opensearch:2.19.1` 基于 Amazon Linux 2023，其 glibc 要求 CPU 至少 **ARMv8.2-a**。在 Cortex-A72、飞腾 FT-2000 这类 ARMv8.0 机器上启动会直接失败：

```
Fatal glibc error: This version of Amazon Linux requires a newer ARM64 processor
compliant with at least ARM architecture 8.2-a with Cryptographic extensions.
```

`opensearch/Dockerfile` 把操作系统层换成 Ubuntu（arm64 基线 ARMv8.0），OpenSearch 本体、内置 JDK、插件和官方入口脚本都从官方镜像原样搬过来，`discovery.type`、`DISABLE_SECURITY_PLUGIN` 等环境变量的处理逻辑不变。因此 compose 里 OpenSearch 的镜像名是 `jiuge-bkn/opensearch:<架构>`，会随应用镜像一起构建和打包。

### 5.4 产物

`openbkn-deploy\build\`：

| 文件 | 说明 |
|---|---|
| `jiuge-bkn-images-amd64.tar` | x86 包，23 个镜像（15 个应用 + 8 个运行期依赖），约 2.6 GB |
| `jiuge-bkn-images-amd64.tar.sha256` | 校验和 |
| `images-amd64.txt` | 镜像清单（带架构列） |
| `jiuge-bkn-images-arm64.tar` | **ARM 包**，同样 23 个镜像，只含 `linux/arm64` |
| `jiuge-bkn-images-arm64.tar.sha256` | 校验和 |
| `images-arm64.txt` | 镜像清单（带架构列） |

> 旧版本产出的 `jiuge-bkn-images.tar`（无架构后缀）仍然可以导入——`load-images.sh` 会先找带后缀的包，没有才回落到旧名字。

cd ..\bkn-studio

### 6.1 校验产物

```bash
cd openbkn-deploy/build
sha256sum -c jiuge-bkn-images-amd64.tar.sha256
sha256sum -c jiuge-bkn-images-arm64.tar.sha256
```

### 6.2 按架构拷贝

先确认内网机架构（`uname -m`：`x86_64` 或 `aarch64`），只拷对应目录即可。

```powershell
$src = "E:\workspace\qy\openbkn\openbkn-deploy"
$dst = "E:\to-intranet\jiuge-bkn-deploy"
New-Item -ItemType Directory -Force "$dst\docker","$dst\build" | Out-Null

Copy-Item "$src\docker\compose.yml","$src\docker\.env",
          "$src\docker\gateway.conf","$src\docker\proxy-headers.conf",
          "$src\docker\mariadb-init.sql","$src\docker\render-config.sh",
          "$src\docker\install-docker.sh","$src\docker\load-images.sh",
          "$src\docker\load-images.ps1",
          "$src\docker\镜像打包说明.md","$src\docker\内网部署说明.md" "$dst\docker"

Copy-Item -Recurse "$src\docker\config.template" "$dst\docker\config.template"

# 按架构二选一
Copy-Item -Recurse "$src\docker\app\amd64" "$dst\docker\app\amd64"
# Copy-Item -Recurse "$src\docker\app\arm64" "$dst\docker\app\arm64"

# 镜像包同样按架构二选一
Copy-Item "$src\build\jiuge-bkn-images-amd64.tar",
          "$src\build\jiuge-bkn-images-amd64.tar.sha256",
          "$src\build\images-amd64.txt" "$dst\build"
# Copy-Item "$src\build\jiuge-bkn-images-arm64.tar",
#           "$src\build\jiuge-bkn-images-arm64.tar.sha256",
#           "$src\build\images-arm64.txt" "$dst\build"
```

> 两个架构都要交付时，`app\` 下的两个子目录和两个镜像包可以一起拷，导入脚本会按本机架构校验并拒绝不匹配的包。

### 6.3 交付清单

- `docker\`（含 `.env` 与 `config.template\`）
- `docker\app\<架构>\`（Docker 安装包）
- `build\jiuge-bkn-images-<架构>.tar` + `.sha256` + `images-<架构>.txt`

**不要**交付：`bkn-foundry`、`bkn-studio` 源码、`docker\config\`、另一架构的 `app\` 子目录、`build\` 下的历史产物。

## 七、常见问题

**构建时拉包失败**

构建阶段需要访问镜像仓库、Go 模块代理、PyPI、npm。仓库里已经配好国内镜像源；如果仍然失败，检查 Docker Desktop 的代理/DNS，或参考 `compose.yml` 顶部各服务的 `GOPROXY_URL`、`PIP_INDEX_URL`、`NPM_REGISTRY` 参数。

**磁盘空间不足**

构建缓存加镜像包通常需要 40 GB 以上；可执行 `docker system prune` 清理旧缓存后重试。

**镜像 tag 不对**

应用镜像统一命名为 `jiuge-bkn/<service>:<tag>`，`<tag>` 取自 `.env` 的 `JIUGEBKN_IMAGE_TAG`（默认 `local`）。改名后需要重新打包。

**内网机架构不一致**

amd64 的镜像包不能导入 arm64 机器。症状是**所有容器 `Restarting (255)`**，日志里是 `exec format error`——不是配置问题，是镜像包拿错了架构。

鲲鹏/飞腾机器用 `bash package-images.sh --arch arm64` 出包，详见 5.2 节。x86 机器上用 buildx + QEMU 交叉构建即可，不需要额外的 ARM 构建机。

导入端已经有硬校验：包架构和本机不一致时 `load-images.sh` / `load-images.ps1` 会在导入阶段直接失败，不会等到起容器才发现。
